# 虚拟工作室重设计规格

## 状态

- 设计状态：方案 A 已确认（2026-10-10，Asia/Shanghai）
- 实施状态：资源已逐项确认，代码接入待开始
- 图片生成状态：背景、角色源图、7×8 转面、桌面、显示屏、骨骼预览与合成预览均已逐项通过
- 目标平台：现有 Coworkany Desktop（当前 macOS 目标）

## 目标

将现有虚拟办公室从“低分辨率合并图集 + 正面剪影”重设计为温暖的 2.5D 卡通虚拟工作室。角色、办公桌和显示屏必须成为可独立替换、独立渲染、独立验收的资源层。

核心角色视觉：大头短身、背对用户工作。角色需要有轻柔的走动、繁忙工作和 thinking 动效，同时保留 React 状态卡片作为完整的可访问与故障回退界面。

## 已确认的视觉决策

### 场景构图

- 采用“岛屿式群像”：7 个角色各占一个独立工位，整体横向可见。
- 宽度不足时优先平滑缩放或横向滚动，不把角色压缩到无法辨认。
- 每个工位从后到前依次为：背景光晕、背影角色、双显示屏、办公桌前沿、状态标记与交互热区。
- 角色处于桌面之后，桌面前沿遮住下半身，强化“正在工作”的姿态。
- 背景工位采用明确的 3+4 岛屿锚点（后排 3 个、前排 4 个），不再使用单行 7 列等距布局；背景保持 2172 × 724 的宽高比并以 contain 方式铺放。

### 角色语言

- 所有角色共享统一的大头短身背影轮廓。
- 通过角色色、胸牌和一个小道具区分 AI 对话、Agent、PPT、工作流、写作、图片和视频角色。
- 角色身份色与运行、等待、失败、完成等状态色分离；状态色不得覆盖身份识别。

### 桌面与显示屏

- 每个工位使用“桌面双屏”方案。
- 主屏显示当前工作摘要，侧屏显示队列或状态。
- 显示屏、支架、状态灯和文案通过独立接口渲染，可单独替换皮肤。

### 动效

- 采用“轻柔循环”节奏：低干扰、可长期观看。
- `idle`：轻微呼吸和肩部起伏。
- `walk`：角色进入或切换工位时的短步行过渡；不改变数据位置。
- `work`：手臂小幅打字，屏幕轻微亮度变化。
- `thinking`：头部轻摆，思考气泡或光点轻微漂浮。
- `waiting`：动作减慢，屏幕保持等待色。
- `completed` / `error`：一次性反馈后回到安全姿势。
- reduced-motion 时保留静态姿势、状态色和文本，不播放循环动画。

### 动画资源形式

- 采用“2D 骨骼 + 纹理图集”方案。
- 角色拆为头发、头部、身体、左右手臂、手部 / 道具、阴影等插槽。
- 骨骼层级：`root → torso → head / arm.l / arm.r → hand / prop`。
- 7 个角色共享骨骼与动画，仅替换皮肤、角色色和道具。
- 当前批准的 rig JSON 是轻量 normalized keyframe 数据，不依赖 Spine/DragonBones；Pixi 动态场景 chunk 内置小型插值器，将骨骼姿态映射为容器变换。后续若需要真正网格变形，可在不改业务数据边界的前提下替换该实现。

## 资源交付边界

图片生成与代码实现分离。以下资源已逐项生成并确认；正式接入仍需通过运行时切片、透明度、尺寸、哈希和预算检查：

1. 完整工作室背景合成图（不含角色，含墙面、地面、光源和 7 个工位槽位）。
2. 角色透明源图与角色皮肤图集（统一背影轮廓、7 个角色色和道具）。
3. 办公桌透明源图与桌面状态图集（可用、工作中、离线）。
4. 主显示屏、侧显示屏、支架和状态光效源图。
5. 骨骼 / 插槽预览图、纹理图集和动画数据草案（覆盖 idle、walk、work、thinking、waiting、completed、error）。
6. 完整合成预览图，用于确认所有独立层叠加后的最终观感。

每一项图片确认至少检查：构图、透明边缘、角色比例、色彩、层级关系、可切片性、与其他资源的组合效果。图片确认不是一次性总批准，用户可以单独退回某一项重生成。

已批准草稿集中在 `docs/superpowers/assets/drafts/2026-10-10-virtual-studio/`，审批记录集中在 `docs/superpowers/assets/2026-10-10-virtual-studio-asset-approval.md`。在全部运行时校验通过前，草稿不得被视为生产资源。

## 交互与数据边界

- `OfficeStore` 继续是唯一状态来源，不新增办公室数据库或任务表。
- 数据流：现有任务 / 运行状态 → `OfficeStore` 快照 → 纯函数视觉状态解析器 → 角色、桌面、显示屏三层渲染。
- 渲染器不得直接读取 WorkbenchClient、Tauri、存储或导航模块。
- Pixi 继续懒加载；React 先渲染完整状态卡片。
- 角色、桌面和主屏点击进入角色入口；侧屏任务标记进入对应工作项。
- Canvas 保持装饰性；键盘、屏幕阅读器、完整文本和故障回退继续由 React 承担。
- 未知状态回退到静态安全姿势，场景加载或资源加载失败时回退到完整 React 视图。

## 预期代码边界（实施阶段）

- 保留 `VirtualOfficeHome`、`OfficeStore`、角色投影、导航和 React fallback 的业务职责。
- 将 `office-scene` 的绘制拆为背景、角色 rig、办公桌、显示屏和状态标记几个 renderer-only 模块。
- 新增纯函数视觉状态解析器和骨骼资源注册接口；不把业务事实复制进 renderer。
- 继续使用版本化 asset manifest、路径校验、哈希校验和动态 Pixi chunk。
- 运行时资源脚本负责将批准的透明 PNG 转为受控 WebP 图集，并生成 manifest 尺寸、帧名、角色顺序和 SHA-256；脚本必须可重复执行，不覆盖草稿。
- `office-scene` 的层序固定为：背景 → 工位底座/桌面后沿 → 角色 rig → 显示屏 → 桌面前沿/遮挡层 → 状态特效与交互热区。若源图只有整桌，切片脚本需同时产出桌面后沿和前沿，避免角色穿过桌面。
- 角色源图先作为整身安全皮肤使用；骨骼插值器对头、躯干、手臂和道具容器做轻量变换。无法切出独立插槽时，必须回退到整身静态姿势，不得伪造网格变形。
- 不引入新的持久化层；不改变现有工作区、会话、任务或媒体页面的所有权。

## 验收标准

### 视觉

- 7 个工位均能识别角色背影、桌面、双屏和状态标记。
- 角色、桌面、屏幕可以单独替换，不需要重新导出整张场景图。
- 角色在 idle、walk、work、thinking 状态下动作清晰但不喧宾夺主。
- 背景中的 3+4 工位锚点与七个角色/桌面实例一一对齐，窗口缩放后仍保持顺序和层级。
- 合成预览与独立素材在比例、边缘和颜色上保持一致。

### 功能与可访问性

- 角色、桌面和屏幕点击导航保持现有复合键工作项语义。
- React fallback 在 Pixi 动态导入、骨骼解析或资源加载失败时完整可用。
- reduced-motion、隐藏窗口和空闲降帧策略继续生效。
- 双语文本、键盘路径、状态标签和最近工作列表不回归。

### 工程与性能

- manifest 包含资源尺寸、插槽 / 动画名称、角色 ID、版本和 SHA-256。
- Pixi 仅进入动态场景 chunk，不进入静态入口。
- 骨骼状态解析、图层顺序、资源注册、失败回退和导航均有自动化测试。
- 完成 macOS 目标下的构建、资源完整性和视觉验收；不宣称 Windows 发布就绪。

### 方案 A 的实施顺序

1. 将已批准草稿登记为不可变输入，生成运行时图集与 manifest。
2. 先接入背景、桌面和显示屏分层，验证 3+4 锚点与遮挡顺序。
3. 接入角色皮肤与 keyframe 插值器，映射真实投影状态到动作，不创建虚假工作项。
4. 运行资源、类型、单元、浏览器场景和 macOS 构建检查；失败时保留 React fallback。
5. 通过视觉验收后再记录 `integrated` 生产路径。

## 非目标

- 不重做现有工作台、会话、任务执行、审批、预览或媒体页面。
- 不新增办公室专属任务数据库。
- 不在未单项确认图片前批量生成或覆盖正式生产素材。
- 不把 Canvas 作为唯一的交互或可访问界面。
